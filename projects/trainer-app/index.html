trAIner

Workout planner · two AI pipelines · live on iOS & Android

A FastAPI + HTMX web app — installable as a PWA — for building routines, logging sessions and getting two genuinely different kinds of AI feedback: an LLM that reads a finished session and returns progression changes you can apply in one tap, and a computer-vision pipeline that scores your lifting technique from an uploaded video. Bilingual throughout (EN/ES). After a private beta with 20 users, it is now publicly released on both the App Store and Google Play.

The Two AI Pipelines

They answer different questions, run on different hardware and reach the browser by different routes. Neither runs inside the request: both are enqueued to Celery, one on a CPU queue and one on a GPU queue.

01

Session analysis — LLM

When you end a session, the app builds a payload of what you actually lifted — sets, targets, recent history, estimated 1RM — and hands it to a Claude Haiku agent through pydantic-ai with a typed output_type, so what comes back is structured and validated, not prose to be parsed. Each per-exercise verdict is an action plus concrete targets, which the UI turns into a one-tap edit of your routine. Results stream into the page over SSE.

The progression rules — conservative overload, deload conditions, unilateral balance — live in the system prompt rather than in the model's assumptions. The payload carries only training data: no name, no email, no identifiers.

02

Technique analysis — computer vision

Upload a video of a set and a GPU worker runs it end to end: preprocess to 15 fps and ≤1920 px, YOLO11m person detection with IoU tracking to hold onto the right athlete, then SynthPose (ViTPose-Huge) for 52 keypoints — including the anatomical spine markers COCO-17 doesn't have. The skeleton is normalized (pelvis origin, torso scale, mirroring) so the numbers survive differences in body size and camera distance, and a 4-state hysteresis machine counts the reps.

Scoring is per exercise, not one method for everything: squat and RDL are judged on relational metrics between joints, while bench press uses DTW against reference reps plus left/right symmetry. Out come an annotated pose.mp4, per-stage JSON artifacts, and named bilingual fault cues from a rule-based feedback service.

This engine has since been extracted into a standalone project — Gym Technique Analyzer, where the metrics and the reference set are documented in full.

The App Around Them

◈ Routine Builder & Session Logging

Drag-and-drop routine building in HTMX, with per-set weight, reps, RPE, RIR and rest. Sessions are logged live against the plan — what you actually lifted versus what was prescribed — and the rest timer fires a Web Push notification that still arrives with the app in the background.

◈ Progression & Estimated 1RM

Estimated 1RM per exercise over time via a modified Epley formula, plotted as a history you can actually read a trend off. Unilateral work keeps left and right as separate series rather than averaging away the imbalance you were trying to see.

◈ Bilingual Exercise Library

Filterable by muscle group, equipment and type, with bilateral, unilateral and temporal execution modes — every entry in both English and Spanish. Users can suggest missing exercises, which land in an admin queue for approval before they reach the catalog.

◈ Social Layer & PWA

Follow other users, like their sessions, share and adopt routines, and compare on per-exercise leaderboards. The whole thing installs as a PWA on iOS and Android — manifest, service worker and an offline fallback page.

Architecture

The app is HTML-first: almost every endpoint returns a Jinja2 partial that HTMX swaps into the page, so there is no client-side state to keep in sync with the server's. Anything slow is never done in the request — it is enqueued to Celery and delivered back over SSE (session analysis) or polling (technique analysis). Layering is strict: routes/ → services/ → models/. 

browser (HTMX + service worker)
   |  HTMX partials + SSE
   v
Cloudflare Tunnel -> FastAPI
                       |
                       +--> PostgreSQL 15 . Redis . file storage
                       |
                       +--> Redis queues
                              |
                              +--> GPU worker x2   pose + scoring
                              +--> CPU worker x8   LLM + Web Push

The two worker pools are separate on purpose: pose estimation would otherwise monopolise the same processes that send notifications and call the LLM. Migrations run on container start (alembic upgrade head), so deploying is pull-and-up.
